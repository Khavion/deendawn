## e2e-testing: State of mobile E2E and quality testing for React Native / Expo apps (mid-2026), applied to DeenDawn (Expo SDK 57 / RN 0.86.0 / React 19.2.3, New Architecture)

### Key findings

- Maestro is the de-facto standard E2E tool for Expo apps in 2026. Latest CLI is 2.8.0, released 2026-07-31 (today). Recent releases (2.5.0–2.8.0, Apr–Jul 2026) are dominated by iOS reliability work: fixed taps after scrollUntilVisible, faster iOS hierarchy retrieval, false app-crash errors on launch fixed, cross-process sheet handling, parallel iOS simulator execution with per-device sessions. Android got a ~41% perf win by replacing TCP port forwarding with direct ADB sockets (2.5.0) and first-party Unicode input (2.7.0) — relevant for DeenDawn's Urdu/Arabic text entry. Android API 35/36 support landed in Q2 2026.
- Maestro's 2026 direction is AI-assisted authoring: redesigned Maestro Studio desktop app (announced 2026-04-21) with device-aware autocomplete, an MCP server (consolidated to 8 tools in 2.5.0) so coding agents can drive test generation, and a Maestro Viewer visualizer (2.6.0). The deprecated Rhino JS engine was removed in 2.6.0 — flows using legacy JS need migration.
- Maestro cloud options: official Maestro Cloud is alive (no shutdown) at roughly $250/device/month (Android or iOS), billed by max concurrency, used by Microsoft/Amazon/Meta teams. devicecloud.dev is a compatible third-party alternative at ~$0.06–$0.14 per unit (per-minute style pricing), same open-source API, marketed as 'twice as fast, half the cost'. Local CLI execution remains free.
- Expo has first-class Maestro CI support: EAS Workflows has a pre-packaged `maestro` job type — a build job (iOS `simulator: true` / Android `buildType: apk` profile) feeds `build_id` into a maestro job with `flow_path: [...]` arrays, triggerable `on: pull_request`. Expo also announced Maestro Cloud integration inside EAS Workflows (run cloud tests next to builds). This is the canonical Expo E2E CI pattern in 2026 and matches DeenDawn's existing e2e/ Maestro suite.
- Detox is effectively behind the curve for DeenDawn's stack: official docs state support for RN 0.77.x–0.84.x only (DeenDawn is on 0.86.0), latest npm version 20.51.4 with RN 0.85.2 only in devDependencies. Detox explicitly maintains no Expo-specific code or docs — Expo integration is 'entirely a community-driven effort'. It is New-Architecture compatible within its supported RN range, but its compatibility historically lags each RN/Expo bump. Not recommended for this project.
- Appium remains alive but niche for RN: Appium 3 shipped Aug 2025, current stable ~3.5.2 (July 2026), requiring Node 20.19+, W3C-only capabilities, ~10–15% faster execution. 2026 guidance consistently positions it as the choice for enterprises with existing suites or multi-framework device farms — not for a greenfield Expo app.
- Unit/component layer: React Native Testing Library v14.0.0 went stable 2026-06-05 (v14.0.1 on 2026-06-23). Breaking: requires React 19+ and RN 0.78+, all core APIs (render, renderHook, fireEvent, act) are now async and return Promises, concurrent rendering is always on (matches New Architecture), react-test-renderer replaced by Callstack's new Test Renderer, Node ^22.13 || >=24 required, UNSAFE_* queries removed. v13.x is now the React-18-only branch. Separately, RN 0.85 (Apr 2026) moved the Jest preset into a dedicated package.
- Visual regression for RN in mid-2026 is still the weakest layer, with three viable paths: (1) react-native-owl (Nearform) — Jest .toMatchBaseline() pixelmatch diffing on simulator/emulator screenshots, store .owl/ output as CI artifacts, but no collaborative review workflow; (2) Chromatic for iOS/Android — announced 2026-05-13, still EARLY ACCESS (not GA): renders Storybook RN stories on hosted iOS simulators/Android emulators with 'SteadySnap' burst-capture stabilization, baseline tracking and PR review UI; (3) Sherlo and Lost Pixel (Storybook-based, self-hostable) as alternatives. Maestro's own takeScreenshot gives raw captures but no diffing.
- SQLite testing: no dominant 'contract test' framework emerged; established practice is (a) expo-sqlite-mock for Jest when exercising expo-sqlite call sites, (b) running real SQL against better-sqlite3 (or in-memory sqlite3) in Node for schema/query behavior, since expo-sqlite and better-sqlite3 both wrap stock SQLite, and (c) golden-file assertions against the actual shipped .db artifact — which DeenDawn already implements via content.lock hashes, ayah counts, and byte-equality tests.
- Consensus 2026 test pyramid (e.g. Plaintest guide, 2026-01-30): every PR = typecheck/lint + unit/component (Jest+RNTL) + a small smoke set of Maestro flows on latest iOS simulator + latest Android emulator; nightly = full E2E suite on cloud devices (latest + previous OS versions), full regression + visual diffs, optional AI-exploration runs; pre-release = exhaustive device-matrix passes (top ~5 iOS / ~10 Android devices) plus accessibility audits. Maestro's built-in wait/retry is credited with taming most flakiness; the historical iOS-flakier-than-Android gap has narrowed substantially through 2026 releases, though the changelog shows iOS still receives the bulk of reliability fixes.

### Recommendations for DeenDawn

- Stay on Maestro as the sole E2E framework; do not adopt Detox (no official RN 0.86 or Expo SDK 57 support) or Appium (wrong fit for a greenfield Expo app). Pin Maestro CLI >= 2.7.0 in CI to get the iOS tap-after-scroll and false-crash fixes — these directly affect long-scroll flows like the surah list; 2.8.0 (released today) adds element-relative swipe points useful for the tasbih/qibla gestures.
- Adopt the EAS Workflows canonical pattern for PR E2E: an `e2e` build profile in eas.json (ios.simulator: true, android.buildType: apk), then a `maestro` job with build_id from needs.<build>.outputs.build_id and flow_path arrays, triggered on pull_request. Keep the PR set to a smoke subset (onboarding, prayer times render, open surah, airplane-mode offline check) and run the full e2e/ suite nightly via a schedule trigger. Free/local alternative: keep the current `xcrun simctl` + `maestro test e2e/` loop for the inner dev cycle — cloud is only needed for device variety.
- If cloud E2E is ever needed, devicecloud.dev (~$0.06–0.14/unit) is far cheaper than Maestro Cloud ($250/device/month) and API-compatible — but both are a Gate 3 (spending money) BLOCKERS.md item for Zohaib; local simulator runs cost nothing and cover DeenDawn's needs today.
- Plan the RNTL v14 migration as a discrete task: it requires React 19 (DeenDawn qualifies at 19.2.3) but makes render/fireEvent/act async — every component test needs await added, and Node must be ^22.13 || >=24 in CI. Since RN 0.85+ moved the Jest preset to a dedicated package, verify jest-expo for SDK 57 before hand-rolling preset config. If the churn is too large mid-phase, stay on latest v13.x (still maintained for now) and schedule v14 for after the iOS TestFlight milestone.
- For visual regression, the pragmatic v1 choice is react-native-owl on the iOS simulator in CI (Jest + pixelmatch, .owl/ artifacts uploaded on failure), covering the 8-cell locale×theme matrix you already sweep manually — it's local, free, and privacy-clean. Watch Chromatic for iOS/Android (early access as of 2026-05-13) but don't build on it yet: not GA, hosted-only, and would add an external service dependency. A zero-new-dependency stopgap: keep Maestro takeScreenshot captures per locale/theme and diff them with pixelmatch in a small Node script on nightly runs.
- For SQLite contract tests, extend the existing golden tests into a Node-side contract suite: open the actual built assets/db/quran.db with better-sqlite3 in Jest and assert the query contracts the app relies on (FTS5 normalized-column matches for known terms, exact verse counts the Tier A 'Ask' layer will surface, surah/juz metadata joins, first/last ayah bytes). For the future op-sqlite + sqlite-vec store, load the sqlite-vec extension in the same Node harness so vector-query contracts are tested without a device. Use expo-sqlite-mock only for thin call-site tests, never as a substitute for real-SQL contract tests.
- Codify the pyramid in docs/TESTPLAN.md as: every commit/PR = tsc, eslint, jest affected (RNTL component + unit fixtures), religious-text checksum test, SQLite contract suite (all run in Node, minutes); per-PR or per-merge = EAS Workflows iOS+Android e2e-profile builds + Maestro smoke flows; nightly = full Maestro suite including the airplane-mode offline suite and screenshot diffs across en/ur/ar × 3 themes; pre-release = the existing human 'Device pass' checklist (magnetometer/qibla, real notification delivery, background audio) which no 2026 tooling can automate on simulators.

### Pitfalls

- Detox docs claim New Architecture support, but only for RN 0.77–0.84; adopting it on RN 0.86/SDK 57 means running an officially untested combination with zero Expo support from the Detox team.
- RNTL v14's async-everything API is a breaking migration (every render/fireEvent call needs await); upgrading Jest config without also bumping Node to >=22.13 in CI will fail. v13.x will not receive React 19 concurrent-mode fixes long-term.
- Maestro 2.6.0 removed the deprecated Rhino JS engine and the bundled Studio — any evalScript flows written against old JS semantics or docs referencing the embedded Studio are stale.
- Chromatic RN visual testing is early access (announced 2026-05-13), not GA — do not architect the visual-regression layer around it yet; it is also a hosted third-party service, which intersects with DeenDawn's no-new-outbound-domain rule (Rule 2) even though it only runs in CI, so document it in DECISIONS.md if ever adopted.
- Visual diffing on simulators is flaky by default: status-bar clock, font smoothing, and animation timing cause false diffs — freeze time/status bar (xcrun simctl status_bar override), disable animations, and use per-platform baselines. RTL (ar/ur) screens double the baseline count; budget for baseline churn on every design-token change.
- better-sqlite3 in Node vs expo-sqlite on device can differ in compiled SQLite version and enabled extensions (FTS5, ICU); pin/verify the FTS5 tokenizer behavior matches on-device (one Maestro search-flow assertion covers the gap). Never let any test harness rewrite the quran.db artifact — contract tests must open it read-only per the NO-AI ZONE rules.
- EAS Workflows maestro jobs consume EAS build credits per run (each E2E run needs a fresh or cached build); wiring the full suite on every PR can get slow and costly — smoke on PR, full suite nightly.
- Search-result claims that Maestro handles iOS and Android 'uniformly' understate reality: the changelog shows iOS-specific reliability fixes landing continuously through July 2026, so keep iOS Maestro CLI pinned and upgrade deliberately, re-running the full suite after each bump.

## ios-review-pitfalls: Apple App Store review in 2026 for prayer/Quran/religious apps: 4.3(b) spam enforcement, zero-collection privacy labels, background audio, location strings, religion-specific rules, RN/Expo and TestFlight gotchas

### Key findings

- GUIDELINES CURRENCY: The App Review Guidelines were revised 2025-11-13 and again 2026-06-08. The June 2026 revision tightened 4.3(b): current verbatim text says Apple 'will not accept new submissions unless they offer a meaningfully different or improved experience' in saturated categories, may remove such apps 'if they are not updated, improved, or do not attract customers,' and warns that repeated low-effort submissions 'may lead to removal from the Apple Developer Program' (fetched live from developer.apple.com/app-store/review/guidelines/ on 2026-07-31; date confirmed by MacRumors 2026-06-09).
- 4.3(b) ENFORCEMENT REALITY (2025-2026 reports): rejections can hit previously approved apps on routine updates; prior approval is not binding. Triggers reported by developers: shared/similar binaries, metadata, concepts, UI, and common template code across submissions; category-level ML flagging can sweep in apps that merely resemble a saturated category (documented Mar-Apr 2026 Apple forum thread 820697 where a B2B dashboard was repeatedly rejected as 'astrology'; Apple staff's only remedies were Resolution Center reply, requesting a phone call, or App Review Board appeal — no documented resolution).
- 4.3(b) DEFENSE PLAYBOOK (from 2025-2026 practitioner guides): in the App Store Connect review-notes field, name concrete differentiators ('our app includes features X, Y, Z that don't exist in [category]; X works by...'), state the specific target user, link a developer/company site tying the author to the domain, attach a demo video in Resolution Center replies, and if Apple names a specific app you resemble, rebut that comparison directly rather than generically. One secondary blog claims 4.3 is ~28% of all rejections — UNVERIFIED, treat as directional only.
- NEW 4.1(c) (added 2025-11-13): you may not use another developer's icon, brand, or product name in your app's icon or name without approval — relevant when naming/branding against incumbents like Muslim Pro.
- RELIGION-SPECIFIC RULE: Guideline 1.1.5 verbatim lists as objectionable content 'Inflammatory religious commentary or inaccurate or misleading quotations of religious texts.' Accuracy of Quran text/translations is thus itself a review-guideline matter, not just an internal quality bar — DeenDawn's checksummed content pipeline is a direct review defense.
- CHARITY: Guideline 3.2.1(vi) verbatim: only 'Approved nonprofits' may fundraise in-app, must offer Apple Pay, disclose fund use, and provide tax receipts; nonprofit platforms must vet every listed nonprofit. DeenDawn's zero-monetization, calculator-only zakat posture stays entirely clear of this.
- PRIVACY LABEL / 'DATA NOT COLLECTED' (Apple's official app-privacy-details page, fetched 2026-07-31): 'Collect' means 'transmitting data off the device in a way that allows you and/or your third-party partners to access it for a period longer than what is necessary to service the transmitted request in real time.' Explicitly: 'Data that is processed only on device is not collected and does not need to be disclosed' — so on-device-only location for prayer times/qibla requires NO disclosure. Also explicitly: an IP address 'sent on a server call and not retained' (e.g., audio streaming) needs no disclosure — meaning 'Data Not Collected' is truthful ONLY if R2/CDN logs don't retain identifiable request data.
- LOCATION: 5.1.1(ii) verbatim: 'Ensure your purpose strings clearly and completely describe your use of the data.' 5.1.5 verbatim: 'Use Location Services in your app only when it is directly relevant to the features and services provided by the app... Ensure that you notify and obtain consent before collecting, transmitting, or using location data.' Vague purpose strings are a top reported 2025 RN/Expo rejection class, and NEW purpose strings are a documented trigger for extended TestFlight beta review.
- BACKGROUND AUDIO: 2.5.4 verbatim: 'Multitasking apps may only use background services for their intended purposes: VoIP, audio playback, location, task completion, local notifications, etc.' Documented rejection pattern (2023-2025, github.com/gdelataillade/alarm discussion 87 + audio_service issue 975): apps declaring the 'audio' UIBackgroundModes key are rejected if reviewers cannot hear audible content while backgrounded, and a reviewer stated (May 2024) 'background audio intended for setting and playing alarms is inappropriate because it can be replicated with Local Notifications' — a stance Apple maintained in a July 2025 rejection. Continuous Quran-recitation streaming with lock-screen controls is the accepted use; adhan must remain local-notification-based (<30s clip, matching DeenDawn's design).
- PRIVACY MANIFESTS: since 2024-05-01, uploads using required-reason APIs must declare NSPrivacyAccessedAPITypes or get ITMS-91053 rejections; still enforced through 2025-2026. Expo supports adding a privacy manifest via app.json/app.config.js, and Expo SDK modules ship their own manifests, but third-party pods outside the SDK (e.g., op-sqlite, llama.rn) must be checked individually.
- COMMON RN/EXPO REJECTIONS reported 2025: (1) privacy policy URL missing/unreachable or not matching actual practices — one 2025 guide attributes ~28% of new-app rejections to privacy-policy accessibility/disclosure (secondary source); (2) weak permission purpose strings; (3) 'thin wrapper'/minimum-functionality pushback; (4) metadata promising features the binary doesn't show; (5) IAP products not ready (N/A for DeenDawn). Note 5.1.1(i) requires the privacy policy link BOTH in App Store Connect metadata AND in-app.
- TESTFLIGHT EXTERNAL (2026 data, ptkd.com 2026-05-18): first build of each version requires Beta App Review; typical clearance 2-7 days (outliers 10-15+ days late 2025 into 2026), with the wait concentrated in 'Waiting for Beta Review' — once 'In Beta Review,' decisions usually land within ~2 hours; subsequent builds of the same version typically process in under an hour. Hard limits: 6 new builds per app per 24h; one build per version in beta review at a time; internal testing (up to 100 ASC users) is instant and bypasses review; external capacity 10,000 invitees. Beta rejections do not affect App Store standing. Extended-review triggers: AI features, new SDKs, new purpose strings, privacy-manifest changes.
- NOV 2025 AI-PRIVACY RULE: 5.1.2(i) now requires clear disclosure and explicit permission before sharing personal data with third parties 'including third-party AI' — DeenDawn's Tier B is on-device-only with no cloud API, so the truthful answer is 'no sharing,' but expect the question if/when Tier B ships.

### Recommendations for DeenDawn

- Write App Review notes (and reuse for TestFlight external review) that defend against 4.3(b) with specifics, not adjectives: lead with 'App Privacy label: Data Not Collected — location computed on-device only, no accounts, no ads, no analytics, no third-party SDKs; every feature works in airplane mode; Quran text is byte-verified against pinned scholarly sources via SHA-256 checksums.' Name 2-3 features category incumbents lack, name the target user, and link a Khavion web page that ties Zohaib's developer identity to the app. This maps exactly onto the June 2026 'meaningfully different or improved experience' bar.
- Include click-by-click reviewer steps in the notes for background audio: 'Open Surah Al-Mulk > tap Play > press Home — recitation continues with lock-screen controls.' Reviewers reject the audio UIBackgroundModes key when they can't personally hear backgrounded audio. Never justify the audio key with adhan/alarms — keep adhan strictly as local notifications with <30s caf/wav clips (already DeenDawn's design; make sure no code path plays adhan via the background-audio session).
- Location purpose string should state on-device-only use and the fallback, e.g.: 'Your location is used only on this device to calculate prayer times and qibla direction. It never leaves your phone. You can enter a city manually instead.' Mention the manual-city path in review notes too — it preempts both 5.1.5 and 'app requires permission to function' pushback.
- Before declaring 'Data Not Collected' in App Store Connect: verify Cloudflare R2/CDN log retention for the audio bucket (retained IP logs arguably count as 'collection' under Apple's definition) — prefer disabling/minimizing access logs and document the retention posture in docs/DECISIONS.md; also confirm what expo-updates/EAS Update transmits and retains, since 'optional update checks' is your only other network surface.
- Host a publicly reachable privacy policy URL before submission — 5.1.1(i) requires it in ASC metadata AND in-app, and unreachable/inconsistent privacy URLs are a top 2025 rejection class. The in-app static screen alone is not sufficient; the marketing-site repo being 'later' makes this a submission blocker to schedule now (a single static page is enough).
- After adding op-sqlite and llama.rn, run expo prebuild and audit the aggregated PrivacyInfo.xcprivacy: confirm required-reason API declarations (file-timestamp, disk-space, UserDefaults categories) exist for every pod, or add them via the Expo app-config privacy-manifest keys, to avoid ITMS-91053 upload rejection.
- TestFlight plan: iterate on internal testing (instant, up to 100 ASC users); when you go external, budget 2-7+ days for the first build of each version, submit early in the week, do not upload additional builds on top of a queued one (6-builds/24h cap, no queue advancement), and avoid version bumps while a build is queued (each new version restarts first-build beta review). New purpose strings and privacy-manifest changes lengthen review — land them in one build, not dribbled across builds.
- Keep Tier B ('Ask') completely out of store metadata, screenshots, and review notes while the flag is OFF — metadata mismatch is a standard rejection, and AI-visible features are a documented extended-review trigger in 2025-2026. When Tier B eventually ships, add a review note: 'On-device model only; no personal data is shared with any third party or third-party AI (guideline 5.1.2(i)); model is a pinned, checksum-verified download from our own bucket.'
- Check 'Deen Dawn' name/icon against existing Islamic apps before app-record creation (4.1(c), new Nov 2025): no resemblance to Muslim Pro, Athan, Quran Majeed marks or icon motifs. Also spot-check that the forest-green + crescent-style iconography (if any) is distinct.
- If a 4.3(b) rejection happens anyway: reply in Resolution Center with the differentiation list plus a short demo video, request the phone call, and only then appeal to the App Review Board; keep tone professional and address any specific app Apple names. Expect that this can recur on updates even after approval — keep the differentiation notes saved and reuse them on every submission.
- Given 1.1.5 ('inaccurate or misleading quotations of religious texts' is objectionable content), mention the content-integrity pipeline in review notes — it is both a differentiator and a compliance answer if a reviewer questions religious content accuracy. Ensure the DEV-translation watermark never appears in release screenshots or the review build's visible UI.

### Pitfalls

- 4.3(b) can strike genuinely original apps: category-level flagging has swept in apps that merely resemble a saturated vertical (Mar-Apr 2026 forum case), prior approval is not binding, and prayer/Quran is a crowded category — treat every submission, including updates, as needing the differentiation notes.
- Declaring the audio UIBackgroundModes key while the most visible audio feature is adhan invites a 2.5.4 rejection; Apple explicitly told developers scheduled/alarm audio 'can be replicated with Local Notifications' (May 2024, reaffirmed July 2025). The reviewer must be able to hear continuous Quran playback in background within a few taps.
- 'Data Not Collected' is falsified by retained server-side logs: Apple's definition exempts IPs only when 'not retained' beyond servicing the request. Default Cloudflare logging or any future analytics/crash SDK silently breaks the label and the review notes built on it.
- No publicly hosted privacy policy URL = submission blocker; the in-app screen alone does not satisfy 5.1.1(i), and unreachable privacy URLs were reportedly a leading 2025 rejection cause.
- TestFlight external: version churn during the queue creates duplicate first-build reviews; resubmitting the same build does not advance position and burns the 6-per-24h cap; expedited review is rarely granted.
- Metadata mismatch: any mention of the Ask feature, adhkar, or reciters not actually enabled in the reviewed binary can trigger rejection.
- Unverified stats: '4.3 = 28% of rejections' and '28% of new-app rejections are privacy-policy related' come from secondary blogs (AlmostDone, NetForemost-adjacent 2025 guides) and could not be confirmed against Apple sources — do not rely on them numerically.
- Not verified this session: whether Apple's reviewers currently apply extra scrutiny specifically to Islamic/prayer apps (no primary evidence found either way); and the exact data-retention behavior of expo-updates/EAS Update servers — check Expo's docs before finalizing the privacy label.

## animation-stack: Reanimated 4.x on RN 0.86 / Expo SDK 57 (New Architecture), mid-2026: CSS animations, layout/entering-exiting, shared elements, expo-router screen transitions, predictive back, and 60/120fps performance patterns

### Key findings

- VERSIONS (verified 2026-07-31): Expo SDK 57 shipped 2026-06-30 with RN 0.86 (from 0.85), React unchanged at 19.2, react-native-reanimated bumped 4.3 -> 4.5, react-native-worklets 0.8 -> 0.10, gesture-handler 2.31 -> 2.32; Expo bills it as a no-breaking-changes release (expo.dev/changelog/sdk-57).
- Latest stable reanimated on npm is 4.5.3 (published ~2026-07-22) with peerDeps react-native '0.83 - 0.86' and react-native-worklets '0.10.x - 0.11.x'. The official compatibility table shows RN 0.86 supported by Reanimated 4.2.x-4.6.x (4.6 pairs with worklets 0.12.x but is not on the npm 'latest' tag yet). Reanimated 4 is New-Architecture-only; legacy arch stays on v3.
- RN 0.86-specific fixes: 4.4.2 fixed 'freezing animations after bump to RN 0.86'; 4.5.3 (and 4.4.3) fixed crashes from withheld EXITING layout animations and animated views reverting to stale values after app pause/re-animation. So on RN 0.86 you want >= 4.4.2, ideally 4.5.3.
- CSS ANIMATIONS API: stable since Reanimated 4.0 (2025-07-23). Full surface today: keyframes via animationName plus animationDuration/Delay/TimingFunction/Direction/IterationCount/FillMode/PlayState, and CSS transitions (transitionProperty/Duration/Delay/TimingFunction). Software Mansion's guidance: use CSS API for state-driven animations (less code, more optimizable), keep worklet APIs (useAnimatedStyle/useSharedValue) for gesture- and scroll-driven animation and multi-value orchestration. String-embedded shared values in transform/filter (e.g. `rotate(${sv.value}deg)`) landed in 4.2.0.
- 4.4.0 (May 2026) added an experimental platform-backed iOS CSS engine behind the static feature flag IOS_CSS_CORE_ANIMATION that runs CSS animations directly on Core Animation layers, bypassing the JS-driven update loop; also precompiled headers cut Android C++ build times, and preallocated synchronous props buffers on Android.
- LAYOUT / ENTERING-EXITING: fully working on New Arch in 4.x with the classic preset families (Fade/Slide/Zoom/Bounce/Flip/etc.), Keyframe, and LinearTransition. Documented New-Arch caveats: overwriting nativeID silently kills entering animations (wrap children in a plain View); exiting animations on children of a removed non-animated parent need collapsable={false} because of view flattening; create animation builders outside components or inside useMemo; springify() entering/exiting not available on web.
- SHARED ELEMENTS: Reanimated re-introduced Shared Element Transitions for the New Architecture in 4.2.0 (2025-12-04) behind the ENABLE_SHARED_ELEMENT_TRANSITIONS feature flag, explicitly 'not intended for use in production'; default transition tweens width/height/origin/transform/backgroundColor/opacity over 500ms, custom animation functions not supported yet, requires react-native-screens 4.19+, and enabling the flag changes layout-animation behavior. As of 4.5.3 it is STILL flagged/experimental — there is no production-blessed shared-element path in Reanimated 4 today.
- The practical custom-transition path in 2026 is react-native-screen-transitions (eds2002, MIT, v3), featured on the official React Navigation blog 2026-04-27: gesture-driven custom screen transitions using a root progress value + screenStyleInterpolator worklets, a Bounds/Boundary API for shared-element-style zoom handoffs (author says it is 'not a traditional shared-element system'), presets for modal/card/shared-transition, snap-point sheets, works with React Navigation native-stack and expo-router, peer deps Reanimated 3 or 4 + gesture-handler v2.
- EXPO-ROUTER NATIVE STACK TRANSITIONS (SDK 57): customization is limited to react-native-screens options — animation presets (default, fade, fade_from_bottom, flip, simple_push, slide_from_bottom, slide_from_right, slide_from_left, none), animationDuration (iOS, only for slide_from_bottom/fade_from_bottom/fade/simple_push; default 350ms; 'default' and 'flip' not customizable), animationTypeForReplace, gestureEnabled (iOS interactive pop, on by default), fullScreenGestureEnabled + fullScreenGestureShadowEnabled (whole-screen swipe-back), gestureDirection (vertical/horizontal), and animationMatchesGesture (make the dismiss gesture drive your chosen animation instead of the default pop). Fully custom JS-driven transitions require swapping to expo-router/js-stack (or the screen-transitions library) — the native stack does not support screenStyleInterpolator.
- ANDROID PREDICTIVE BACK: react-native-screens maintainers (kkafar) stated fragment-level predictive back 'highly likely won't ever be done in react-native-screens v4' (needs FragmentManager back stack, conflicting with their synchronous fragment transactions); it is being researched for the next major. Meanwhile RN 0.81+ enables predictive back for apps targeting Android 16 (API 36), where legacy KEYCODE_BACK/onBackPressed callbacks are gone; known expo-router bug (expo/expo #39092): with predictive back enabled, the back gesture exits to the home screen instead of popping the stack. Workarounds: set android.predictiveBackGestureEnabled: false in app.json (or android:enableOnBackInvokedCallback="false"). So: no in-stack predictive-back animation on Android in 2026; plan to disable it.
- NATIVE TABS: expo-router NativeTabs is still alpha (imported from expo-router/unstable-native-tabs), SDK 54+; renders iOS 26 Liquid Glass automatically, classic tab bar on iOS 18-; Android distinct selected icons need SDK 56+ (react-native-screens 4.25+). SDK 57 also added Stack.Toolbar.Badge in header left/right and Android toolbar menu icons.
- PERF CEILINGS / 120HZ: Reanimated has supported 120fps since PR #2636; Android follows the display's refresh rate natively; on iOS ProMotion you must add CADisableMinimumFrameDurationOnPhone=true to Info.plist or animations cap at 60fps. Reanimated animations run on the UI thread so they survive JS-thread blockage, but heavy useAnimatedStyle worklets, deep view trees, and React re-renders during animation are still the ceiling.
- KNOWN PERF ISSUES mid-2026: (1) Hermes V1 + reanimated causes a 25-30% memory increase on SDK 56 and 57 (Expo-documented known issue; workaround = enable worklets Bundle Mode); (2) Worklets Bundle Mode in DEVELOPMENT builds re-evaluates the whole JS bundle per extra Hermes runtime — up to ~4x bundle size in RAM per runtime, degraded perf on low-end devices; in PRODUCTION bytecode is used, no re-evaluation, and memory can actually be lower than non-bundle mode; (3) opt-in perf flags since 4.2.0: FORCE_REACT_RENDER_FOR_SETTLED_ANIMATIONS (measured ~3x improvement on complex apps by idling settled components) and USE_COMMIT_HOOK_ONLY_FOR_REACT_COMMITS (fixes scroll-sync jank by restricting shadow-tree sync to React-originated commits).

### Recommendations for DeenDawn

- Stay exactly on the SDK 57 pins: reanimated 4.5.x (>= 4.5.3 for the stale-value + exiting-animation crash fixes on RN 0.86) with react-native-worklets 0.10.x-0.11.x. Do not adopt 4.6.x/worklets 0.12 early — it is not the npm 'latest' tag and Expo hasn't validated it against SDK 57.

If a surah-card -> reader zoom transition is ever wanted, use react-native-screen-transitions (MIT, Reanimated 4 + expo-router compatible, React-Navigation-blessed) on that one route group instead of Reanimated SET — but the native-stack defaults are the safer premium baseline for v1.

## ios-widgets-live-activities: iOS home-screen widgets (WidgetKit) and Live Activities for an Expo SDK 57 CNG app (DeenDawn prayer countdown), as of 2026-07-31

### Key findings

- BEST ROUTE CHANGED IN 2026: Expo shipped an official first-party package, `expo-widgets`, announced on the Expo blog 2026-03-04 (launched as alpha). It builds iOS home-screen widgets AND Live Activities as React components using `@expo/ui/swift-ui` primitives — no separate Xcode target, no manual App Groups, no SwiftUI layout code; CNG generates the widget extension target during prebuild. Docs exist under docs.expo.dev/versions/v57.0.0/sdk/widgets/ so it is available on DeenDawn's exact SDK (community articles state SDK 56+ required; DeenDawn is on 57). iOS-only, iOS 16+; requires a development build / EAS Build (not Expo Go).
- expo-widgets API (verified in v57 docs): widget components are plain functions marked with a 'widget' directive, registered via createWidget()/createLiveActivity(). Widgets refresh via updateSnapshot() (immediate), updateTimeline() (pre-scheduled future entries — ideal for prayer times), and reload(). Live Activities: ActivityDef.start(props, url) → instance.update(props) → instance.end(dismissalPolicy, props, contentDate); optional push tokens (push-to-start via addPushToStartTokenListener, per-activity via instance.getPushToken()) only when enablePushNotifications: true in the config plugin. Supported families: systemSmall/Medium/Large/ExtraLarge + accessoryCircular/Rectangular/Inline (lock screen).
- COUNTDOWN WITHOUT REFRESH BUDGET: `@expo/ui/swift-ui` Text supports timerInterval (lower/upper dates) with countsDown, plus date/dateStyle auto-updating text — the system renders a live per-second countdown inside a widget or Live Activity with zero timeline refreshes and zero network. This maps directly onto a next-prayer countdown and works offline (fits DeenDawn's airplane-mode invariant).
- App Group data sharing: the expo-widgets config plugin auto-configures groupIdentifier defaulting to group.<bundleIdentifier>; data reaches the widget as serialized props through updateSnapshot/updateTimeline — the widget never runs your JS at render time and cannot query expo-sqlite. The correct pattern for DeenDawn: compute prayer times in JS with the adhan engine and push a 24–48h timeline of entries; do NOT try to share quran.db or the user-data sqlite file with the extension.
- FALLBACK/COMPLEMENT ROUTE: @bacons/apple-targets (EvanBacon/expo-apple-targets) is actively maintained — npm registry shows v5.0.0 published ~2026-05-13 (epoch 1778698739867 ms), v4.0.6 ~2026-02-28; repo has 425 commits, 1.4k stars, 47 open issues. It supports 40+ target types including widget, watch widget, and iOS 18+ Control widgets, scaffolds via `npx create-target widget`, keeps targets in a root /targets dir surviving prebuild, and shares data via App Groups + NSUserDefaults through its ExtensionStorage native module (set/get/remove + reloadWidget()/reloadControls()). Requires CocoaPods 1.16.2+, Xcode 16, Expo SDK 53+. This route requires you to write real SwiftUI: TimelineProvider/TimelineEntry for widgets, ActivityAttributes + ActivityConfiguration + DynamicIsland closures for Live Activities. With expo-widgets, zero SwiftUI is needed.
- EAS BUILD: documented support for extra iOS targets. For CNG projects, declare extensions under extra.eas.build.experimental.ios.appExtensions in app.json so EAS CLI knows extension bundle IDs before the build and generates per-target provisioning profiles/certificates automatically, including App Group entitlements; EAS also auto-detects targets in the Xcode project for bare workflows. expo-apple-targets README: code signing 'theoretically handled entirely by EAS Build' (only App Clips still need manual signing attention — not widgets).
- LIVE ACTIVITY PLATFORM CONSTRAINTS (Apple): active for max 8 hours, then remains on the Lock Screen up to 4 more hours stale (12h total). Without APNs push, an activity can only be started while the app is running; push-to-start (remote start) exists since iOS 17.2 but requires a server sending ActivityKit pushes. Requires iOS 16.1+ (16.2 for some APIs); Dynamic Island only on iPhone 14 Pro and later. instance.update() from JS requires the app to be alive — a suspended app cannot update its Live Activity without push.
- iOS 18+ ICONS: dark/tinted app-icon variants are NOT mandatory — iOS auto-generates them if you provide only a light icon, but Apple recommends supplying purpose-built variants (dark = transparent-background glyph on dark, tinted = grayscale). Expo supports this natively in app.json: ios.icon = { light, dark, tinted } (since SDK 52 prebuild-config), and SDK 54+ additionally accepts an Icon Composer .icon directory path for ios.icon — DeenDawn on SDK 57 can use either. iOS 18 Control widgets (Control Center / Lock Screen / Action button controls) are NOT documented in expo-widgets; they are available via @bacons/apple-targets' control target template (Swift required).
- MATURITY CAVEAT (dated): expo-widgets launched as alpha 2026-03-04; open docs issue expo/expo#43789 (filed 2026-03-09, assigned, unanswered as of fetch) flags undocumented areas: deep-linking from tapping a standard widget, WidgetKit content-margin handling (a contentMarginsDisabled option exists), and light/dark theming guidance. The v57 docs page itself no longer shows an alpha warning banner, but treat edge cases as unproven.

### Recommendations for DeenDawn

- Adopt `expo-widgets` (already compatible with your pinned SDK 57 / RN 0.86) for the home-screen widget epic: a next-prayer countdown widget in systemSmall + systemMedium plus accessoryRectangular/accessoryInline for the Lock Screen. Add the config plugin with groupIdentifier group.<bundleId> and enablePushNotifications: false.
- Data path: after every notification-reschedule pass (you already run one on foreground/background task), also write a widget timeline via updateTimeline() with one entry per prayer boundary for the next 24–48h, each entry carrying next-prayer name + its Date. Render the countdown with @expo/ui Text timerInterval + countsDown so it ticks offline with no refresh budget and no network — this keeps the 'Data Not Collected' and airplane-mode invariants intact with zero new outbound domains.
- Ship the Live Activity as a lower-priority follow-on, started only when the user opens the app near a prayer window (e.g., within 2h of next prayer, or a suhoor/iftar Ramadan activity — both fit the 8h cap). Keep enablePushNotifications false permanently: push-to-start/update needs an APNs server, which violates privacy rule 2 (new outbound infrastructure) — log this rationale in docs/DECISIONS.md. Design the activity to be self-sufficient: timerInterval countdown + a contentDate/staleDate at prayer time, and end/refresh it opportunistically whenever the app next runs, since you cannot update it while suspended.
- Keep @bacons/apple-targets v5.0.0 as the documented escape hatch (log in DECISIONS.md, don't install yet): use it only if expo-widgets alpha gaps block you (theming/margins/deep-link) or if you later want an iOS 18 Control widget (e.g., 'Open Qibla' / 'Tasbih +1' in Control Center) — that route needs hand-written SwiftUI and Swift Control code.

### Pitfalls

- expo-widgets is ~5 months old (alpha at March 2026 launch): deep-linking from widget taps, content margins, and light/dark theming are undocumented (expo/expo#43789 open, unanswered) — prototype the tap-through-to-app and dark-mode rendering on day one before committing the epic.
- Widgets never execute your JS at render time — do not attempt to read expo-sqlite/quran.db from the extension or move DBs into the App Group container; serialize small computed props (next prayers only) through the timeline/snapshot API.
- Live Activities cannot be started or updated in the background without an APNs push server (iOS 17.2 push-to-start), which DeenDawn's privacy rules preclude — so the Live Activity only exists when the user opened the app that day; don't promise 'automatic prayer countdown on lock screen' in store copy.
- Live Activity hard limits: 8h active / +4h stale, iOS 16.1+, Dynamic Island only iPhone 14 Pro+ — gate UI copy and feature detection accordingly.
- iOS 64-local-notification cap is separate from WidgetKit's refresh budget; pre-scheduled timeline entries + timerInterval text avoid the budget, but frequent reload() calls from JS are throttled by the system — don't call reload() on every app event.
- If you ever fall back to @bacons/apple-targets: never hand-edit generated ios/.targets files; widget signing is EAS-automated but App Clips are not; requires Xcode 16 + CocoaPods 1.16.2+ — check your CI toolchain.
- Mixing expo-widgets and @bacons/apple-targets widget targets in one app is unproven territory — pick one per widget surface.
- The pinned RN 0.86.0/SDK 57 constraint in CLAUDE.md is safe here: expo-widgets and the config plugin work within SDK 57; do not bump SDK to chase newer expo-widgets features without the BLOCKERS.md process.
- Custom Arabic fonts (Amiri Quran) inside the widget extension may need explicit font embedding in the target — unverified this session; test before designing widget typography around them.
- Tinted icon auto-generation by iOS can wreck a detailed brand icon — supply explicit variants rather than relying on system generation, but know it is optional, not an App Review requirement.

## rn-accessibility: Gold-standard React Native accessibility (2026): VoiceOver/TalkBack patterns for custom components, Dynamic Type, reduced motion with Reanimated 4, RTL quirks, audit tooling, WCAG 2.2 mobile mapping, and an executable audit checklist

### Key findings

- CUSTOM COMPONENT PATTERN (verified in current RN docs, applies to RN 0.86): a slider-like control = accessibilityRole="adjustable" + accessibilityValue {min, max, now, text} + accessibilityActions [{name:'increment'},{name:'decrement'}] + onAccessibilityAction. VoiceOver triggers increment/decrement with swipe up/down on the focused element; TalkBack triggers them with the volume-up/volume-down keys. accessibilityValue.text overrides min/now/max when set — use it for human-readable values.
- Custom actions (e.g. 'reset counter', 'next ayah') require a `label` field (that is the localizable, spoken string). VoiceOver exposes them via the rotor/swipe-up-down actions list; TalkBack via its actions menu. iOS-only standard actions: 'magicTap' (two-finger double-tap — the canonical play/pause gesture for audio players; system falls back to Music app if unhandled) and 'escape' (two-finger Z). Android-only: 'longpress', 'expand', 'collapse'.
- Live announcements are asymmetric: accessibilityLiveRegion / aria-live ('polite'|'assertive') are ANDROID-ONLY in React Native. On iOS you must call AccessibilityInfo.announceForAccessibility(), or announceForAccessibilityWithOptions(msg, {queue:true}) (iOS-only queue option) to avoid interrupting speech. 'announcementFinished' event is iOS-only.
- Focus order: RN now has experimental_accessibilityOrder (nativeID array; exhaustive and nestable; cannot combine with accessible={true} on the same node) — documented as experimental in current RN docs (community sources say it landed ~0.82, so it exists in 0.86). Community fallbacks: View collapsable={false}, or the react-native-a11y-order native library (iOS+Android).
- DYNAMIC TYPE (RN Text docs, current): allowFontScaling defaults true; maxFontSizeMultiplier (undefined=inherit, 0=no max, >=1=cap); dynamicTypeRamp is iOS-only, default 'body', values caption2|caption1|footnote|subheadline|callout|body|headline|title3|title2|title1|largeTitle — it puts each text style on Apple's proper Dynamic Type curve. Community-established caps: never below 1.2; tiered caps such as ~2.0 for body/small text, ~1.3–1.5 for large headings.
- Android 14+ (DeenDawn targets API 36) applies NON-LINEAR font scaling up to 200% automatically to sp-based text: small text scales aggressively (8sp can exceed 2x), large text barely (57sp reaches ~112% at the 200% setting). Consequence: do NOT manually multiply by fontScale (double-scaling bug), and line-height must be in scalable units or text gets cramped. Test at the 200% setting. (Verified via Android 14 feature docs + Flutter's migration note describing FontScaleConverter behavior.)
- REDUCED MOTION (Reanimated docs, current, applies to Reanimated 4.5): ALL Reanimated animations default to ReduceMotion.System — with the OS setting on, withSpring/withTiming jump straight to the target, withDecay returns current value, withRepeat skips or runs once, entering/keyframe/layout animations reach endpoints instantly, exiting animations and shared transitions are omitted. useReducedMotion() reads the setting synchronously (unlike AccessibilityInfo.isReduceMotionEnabled()) but reflects the value at app start; ReducedMotionConfig can override globally. Known issue #6714: animation callbacks may not fire while reduce-motion is active — do not gate app logic on animation completion callbacks.
- AccessibilityInfo current surface: isScreenReaderEnabled / isReduceMotionEnabled / screenReaderChanged / reduceMotionChanged are cross-platform; isReduceTransparencyEnabled, isBoldTextEnabled, prefersCrossFadeTransitions, boldTextChanged are iOS-only; accessibilityServiceChanged is Android-only. setAccessibilityFocus is DEPRECATED — use sendAccessibilityEvent(hostInstance, 'focus').
- RTL QUIRKS (Apple dev forums + appt.org, verified): with device language RTL, VoiceOver builds the reading order right-to-left — including for content you laid out LTR (documented number-pad case reads 3>2>1>6>5>4); swipe-next/previous semantics follow language direction, so mixed LTR/RTL screens (Arabic ayah + English translation) can produce a confusing focus path. Fixes are explicit ordering (experimental_accessibilityOrder / native accessibilityElements) and testing each locale separately. Custom action `label`s must go through i18n (react-i18next) or ur/ar users hear English action names.
- TOOLING — what actually works in 2026: (1) Xcode Accessibility Inspector: free, runs audits against the iOS Simulator, explicitly recommended by RN docs for simulator testing. (2) Google 'Accessibility Scanner' (com.google.android.apps.accessibility.auditor, v2.5.1 updated 2026-04-09, Android 6+): free Google app, framework-agnostic (works on RN), flags contrast <3.0, touch targets, missing labels. (3) axe DevTools Mobile 2025.7.x: explicit React Native support via Appium drivers, native XCUITest/Espresso frameworks, and a no-source-code Mobile Analyzer; added WCAG 2.2 touch-target-spacing rules and iPadOS support; COMMERCIAL (license via Deque helpdesk); the free part is the axe Accessibility Linter (VS Code) with 6 RN rules (roles/actions/states/values/image labels). (4) 'GrapheneOS a11y scanner' does NOT exist as a product — GrapheneOS only ships AOSP accessibility features and fills gaps from missing Google services; the Scanner is a Google Play app, so audit on a stock Pixel/emulator (it can run on GrapheneOS only via sandboxed Play).
- WCAG 2.2 MOBILE MAPPING: 'Guidance on Applying WCAG 2.2 to Mobile Applications (WCAG2Mobile)' — W3C Group DRAFT Note, first published 2025-05-06 by the Mobile Accessibility Task Force; informative, not a new standard; still a Draft Note as of this check. It maps all Level A/AA criteria to native apps, replacing 'web page' with 'screen/view' as the conformance unit. Most mobile-relevant criteria: 1.3.4 Orientation, 1.4.10 Reflow, 2.4.3 Focus Order, 2.5.1 Pointer Gestures, 2.5.7 Dragging Movements, 2.5.8 Target Size Minimum (24px minimum; platform guidance 44pt iOS / 48dp Android remains the practical bar), 2.4.11 Focus Not Obscured, 3.3.7 Redundant Entry, 4.1.3 Status Messages.
- APP STORE: Apple's Accessibility Nutrition Labels are live in App Store Connect (introduced 2025). Nine declarable features: VoiceOver, Voice Control, Larger Text, Dark Interface, Differentiate Without Color Alone, Sufficient Contrast, Reduced Motion, Captions, Audio Descriptions. Currently voluntary; Apple has publicly stated they will eventually become mandatory for new apps and updates (no date published as of 2026-07-31). Apple publishes per-feature evaluation criteria (e.g. VoiceOver evaluation criteria) that developers must self-verify for 'all common tasks'.

### Recommendations for DeenDawn

- QIBLA COMPASS DIAL: make the whole dial ONE accessible element (accessible={true}) with accessibilityLabel like 'Qibla direction' and accessibilityValue.text like 'Qibla is 34 degrees to your left'. NEVER announce every heading tick — throttle announcements (announceForAccessibility on iOS, accessibilityLiveRegion='polite' Text on Android) to significant changes (e.g. crossing 15-degree buckets) and fire a distinct announcement + haptic when aligned ('Facing qibla'). That haptic/announcement also satisfies WCAG 1.4.1 (not color/rotation alone). Under useReducedMotion(), snap the needle instead of animating rotation (Reanimated 4 does this automatically for withTiming/withSpring, but verify any sensor-driven direct animation).
- TASBIH COUNTER RING: expose as role='adjustable' (or 'button' + actions) with accessibilityValue {min:0, max: cycle length, now: count} so VoiceOver swipe-up / TalkBack volume-up increments without hunting for the tap target; add custom action {name:'reset', label: t('tasbih.reset')}. Announce only milestones (33/66/99/100) rather than every count — every-tap announcements make the counter unusable with a screen reader. Keep the existing haptic as the non-speech feedback channel.
- AUDIO PLAYER (Quran recitation): implement magicTap → play/pause (accessibilityActions [{name:'magicTap'}] on the player screen root, iOS-only, with a normal Play/Pause button for everyone else); label the play button by the ACTION it performs ('Pause' while playing); make the seek bar role='adjustable' with accessibilityValue.text 'Ayah 5 of 7' or '2 minutes 10 seconds of 4 minutes', increment/decrement seeking one ayah (more useful than seconds for Quran); lock-screen controls come from expo-audio's now-playing metadata and are natively accessible — verify metadata (surah name, reciter) is set.
- DYNAMIC TYPE ROLLOUT: since DeenDawn already routes all text through src/components/ui/AppText, wire tokens.ts variants to dynamicTypeRamp on iOS (body→'body', headings→'title2'/'title3', captions→'footnote') and set tiered maxFontSizeMultiplier: ~2.0 body/small, ~1.5 headings, never below 1.2 on anything users must read. Do NOT sprinkle allowFontScaling={false}; reserve it for the compass degree readout inside the dial if layout demands, and give that data a scalable text alternative. On Android trust non-linear scaling: sp-equivalent sizes, scalable line-height — critical for Noto Nastaliq Urdu at lineHeight 1.9–2.1.
- QURAN TEXT SCALING: test Amiri Quran ligature rendering and ayah-marker layout at iOS AX5 largest size and Android 200% — Arabic script with tight lineHeight is where scaled text clips. Allow generous scaling of Quran text (low-vision users are a core audience for a Quran reader); cap only if rendering breaks, and record the cap in DECISIONS.md.
- REDUCED MOTION: rely on Reanimated 4's ReduceMotion.System default for all withTiming/withSpring/layout animations; add a useReducedMotion() guard for anything Reanimated doesn't own (expo-router transitions, looping 'pulse' effects, the counter ring fill). Subscribe to AccessibilityInfo 'reduceMotionChanged' if you need mid-session updates, since useReducedMotion reflects app-start state. Never attach app logic (navigation, state commits) to animation completion callbacks — issue #6714 means they can be skipped under reduced motion.
- RTL/LOCALE A11Y: run the full screen-reader pass 3 times (en/ur/ar). In ur/ar verify: focus order on mixed-direction screens (ayah + translation), swipe-next direction feels natural, all custom action labels and accessibilityLabels come from i18n keys, and numerals in the tasbih/zakat screens are announced correctly. Use experimental_accessibilityOrder (or collapsable={false}) to pin order on the prayer-times grid and Quran reader if the default order breaks in RTL.
- TOOLING FOR THIS PROJECT (zero budget): free stack = Xcode Accessibility Inspector audits on the iOS Simulator (fits the existing simctl/Maestro workflow) + Google Accessibility Scanner on a stock Android emulator (API 36 image with Play) + axe Accessibility Linter VS Code extension / eslint-plugin-react-native-a11y in CI. Skip axe DevTools Mobile (commercial license, conflicts with the no-spend gate). Do NOT plan audits around GrapheneOS — it has no scanner of its own; use stock images. Add manual VoiceOver/TalkBack passes to docs/TESTPLAN.md 'Device pass (human)' since simulators can't fully replicate gesture behavior.
- STORE PREP: draft Accessibility Nutrition Label answers in fastlane/metadata now (realistic targets: VoiceOver, Larger Text, Dark Interface, Sufficient Contrast, Reduced Motion, Differentiate Without Color Alone) and verify each against Apple's per-feature evaluation criteria before Zohaib submits — they are voluntary today but Apple has said they become mandatory, and DeenDawn's privacy/a11y story strengthens the 4.3(b) review notes. This is part of gated store submission, so put the final label choices in BLOCKERS.md for sign-off.
- EXECUTABLE AUDIT CHECKLIST (one test session, per platform, per locale): [1] Settings: enable VoiceOver (iOS) / TalkBack (Android). Swipe through every screen — every interactive element is reachable, has a label (no 'button' or filename announcements), states announced (selected tab, toggles), decorative icons skipped (aria-hidden/importantForAccessibility='no-hide-descendants'). [2] Focus order matches visual/logical order on: prayer times list, Quran reader (Arabic then translation), settings — repeat in ar with I18nManager RTL on. [3] Compass: focus dial → hear direction value; rotate device → announcements throttled, not continuous; alignment announced + haptic. [4] Tasbih: increment via swipe-up (iOS) / volume-up (Android); count value announced on demand; reset reachable via actions menu/rotor. [5] Audio: magicTap toggles play/pause from anywhere on player screen (iOS); play button label flips Play/Pause; seek slider adjustable by ayah; lock-screen shows correct metadata. [6] Dynamic Type: iOS largest AX size + Android 200% — no clipped/overlapping text on onboarding, prayer cards, Quran (Amiri), Urdu (Nastaliq), zakat form; all screens scrollable to reach content. [8] Contrast: run Accessibility Inspector audit (iOS) + Accessibility Scanner (Android) on every screen in all 3 themes — text >=4.5:1, large text/icons >=3:1 (check bronze/gold on ivory especially). [9] Touch targets >=44pt/48dp: tasbih ring, player controls, ayah bookmark icons, tab bar. [11] Airplane mode + VoiceOver: offline features still fully announced (no silent failed states). [12] Status messages: adhan scheduled confirmations, bookmark saved, zakat result — announced via live region (Android) / announceForAccessibility (iOS) without moving focus. ### Pitfalls

- accessibilityLiveRegion and aria-live silently do nothing on iOS — every dynamic-status feature needs the dual path (Android live region + iOS announceForAccessibility) or iOS users hear nothing.
- TalkBack's increment/decrement on 'adjustable' uses the volume keys — undiscoverable for many users; always provide an accessibilityHint and keep visible +/- buttons as a parallel path.
- Announcement spam: compass headings and tasbih counts announced on every change render the screen reader unusable; throttling/milestone logic is a requirement, not polish.
- maxFontSizeMultiplier had a known Fabric (New Architecture) regression on Text (facebook/react-native #35658). DeenDawn runs New Architecture on RN 0.86 — verify the caps actually apply on device before trusting them; unverified this session whether the fix is in 0.86.
- Reanimated reduce-motion skips can swallow animation callbacks (#6714) — chaining navigation or state changes off withTiming callbacks breaks for reduce-motion users.
- useReducedMotion() returns the setting as of app start; a user toggling it mid-session isn't reflected without an AccessibilityInfo 'reduceMotionChanged' listener.
- Double font scaling on Android 14+: any manual PixelRatio.getFontScale() math on top of sp-based sizes now over-scales because the OS applies a non-linear curve itself.
- RTL focus order follows device language, not your layout — LTR-forced sublayouts (numbers, English translation blocks) get read right-to-left anyway; only explicit ordering fixes it.
- experimental_accessibilityOrder is exhaustive (unlisted siblings become unreachable) and still experimental — use surgically and E2E-test reachability after adopting it.
- 'GrapheneOS a11y scanner' is a misconception — no such tool; Google's Accessibility Scanner needs Google Play (sandboxed on GrapheneOS at best). Budgeting audit time for it wastes a session.
- axe DevTools Mobile requires a paid Deque license (spend = human gate for this project); only the VS Code linter is free.
- WCAG2Mobile is a DRAFT Note (2025-05-06) — cite it as guidance, not a compliance standard, in store/review notes.
- Apple Nutrition Labels are self-declared but Apple publishes evaluation criteria; over-claiming (e.g. Voice Control without testing) is a store-integrity risk — declare only what the audit checklist has verified.

## rn-performance: RN 0.86 + Expo SDK 57 performance tooling and budgets (verified as of 2026-07-31)

### Key findings

- Expo SDK 57 released 2026-06-30 with React Native 0.86 (released 2026-06-11) and React 19.2; billed as a no-breaking-change release. Highlights: light/dark mode emulation in React Native DevTools, edge-to-edge fixes, rendering/animation fixes (expo.dev/changelog/sdk-57; reactnative.dev 0.86 blog).
- STARTUP/PERF PROFILING — Flipper's replacement is the built-in React Native DevTools (Chrome DevTools Protocol on Hermes; press `j` in the Metro terminal). Panels: Console, Sources, Network (Expo), Memory (heap snapshots), Components, and a Profiler for JS performance. RN 0.86 also added a PerformanceObserver durationThreshold spec fix; a custom 'React Native Renderer' track in performance traces landed in this release line (docs.expo.dev/debugging/tools/, reactnative.dev 0.86 blog).
- 'react-native-startup-profiler' does NOT exist as an established npm package (npm/GitHub searches, 2026-07). The real tools are: (a) margelo/react-native-release-profiler — passive Hermes profiling in RELEASE/production builds via startProfiling()/stopProfiling(); traces open in Speedscope, Perfetto UI, or chrome://tracing; needs @react-native-community/cli in Expo projects; (b) Xcode Instruments / Android Studio profilers for native startup (Expo's official recommendation for native runtime analysis).
- Rozenite (Callstack, rozenite.dev) is the 2025/26 plugin framework for React Native DevTools — plug-and-play panels: network activity, performance marks, Redux DevTools, TanStack Query, File System, plus an official Expo Atlas plugin. Works with Expo and Metro. As of Jan 2026 it also has 'Rozenite for Agents' (AI reads component tree/perf/logs).
- Expo Atlas is now STABLE (no longer EXPO_UNSTABLE_ATLAS): `EXPO_ATLAS=true npx expo start` then Shift+M, or `EXPO_ATLAS=true npx expo export` + `npx expo-atlas .expo/atlas.jsonl` for production bundle analysis; resolves unmapped regions generic source-map tools miss (docs.expo.dev/guides/analyzing-bundles/).
- HERMES — Hermes V1 is default since Expo SDK 56 / RN 0.85 (rewritten compiler, new bytecode format, concurrent GC); community reporting cites 25–40% faster cold start from AOT bytecode compilation. Expo SDK 56 also claimed 40% faster Android cold starts and enabled bytecode diffing by default (~58% smaller OTA updates). Hermes sampling profiler is exposed through the DevTools Profiler panel (dev) and react-native-release-profiler (release).
- CRITICAL for DeenDawn: known SDK 57 regression — with Hermes V1, merely importing react-native-reanimated raises app memory 25–30% even if unused (facebook/react-native issue #57059; documented in the SDK 57 changelog). Workaround per Expo: enable Worklets Bundle Mode. Worklets 0.10 (bundled with reanimated 4.5 in SDK 57) declares Bundle Mode 'stable and the recommended way'; Legacy Eval Mode (still the default) can alternatively opt in to evaluating worklets from Hermes bytecode in production. Permanent Hermes fix is pending upstream.
- Caveat: Bundle Mode has its own HIGH memory consumption in DEVELOPMENT (worklet runtimes re-evaluate the JS bundle, up to ~4x bundle size per extra runtime — reanimated issue #9913); this does not apply to production builds, where Bundle Mode memory can be LOWER than eval mode.
- REACT COMPILER — v1.0 stable upstream since 2025-10-07 (react.dev/blog). On Expo SDK 57 it is still EXPERIMENTAL and OFF by default: enable via `experiments.reactCompiler: true` in app config (auto Babel wiring since SDK 54, lint rules default since SDK 55). Only optimizes app code (not node_modules), function components only, must pass the compiler health check. Reported real-world gains: 20–40% fewer unnecessary re-renders (Meta production surfaces, community reports).
- FLASHLIST v2 — New Architecture ONLY (won't run on old arch). No size estimates anymore (estimatedItemSize/estimatedListSize removed). Tuning surface: maintainVisibleContentPosition ON by default (with autoscrollToBottomThreshold, startRenderingFromBottom), maxItemsInRecyclePool for many item types, onStartReached/onStartReachedThreshold, masonry prop, and recycling-aware hooks useRecyclingState (auto-resetting state), useLayoutState, useMappingHelper for keys in .map(). RTL support added; scrollToIndex now precise (shopify.github.io/flash-list/docs/v2-changes/).
- TTI BUDGETS (2026 community consensus): cold-start TTI under 2.0s on mid-tier Android (Pixel 6a-class) and under ~1.2s on iPhone 13-class; RN runtime+bundle overhead measured ~250–280ms on Pixel 7-class, 600ms+ on low-end. Track TTID (first frame) and TTFD (fully interactive) separately. DeenDawn's existing <2s iPhone-12 budget is consistent with, and slightly looser than, premium-app norms.
- MEMORY CEILINGS — iOS jetsam per-process foreground limit is per-device: ~2098 MB on iPhone 12-class (4 GB RAM), ~2.2–2.3 GB on iPhone 13 with the increased-memory-limit entitlement, but roughly 900 MB–1.4 GB on 3 GB devices (iPhone SE 2/3 class). There is NO separate documented fixed limit for background-audio apps: an app actively playing audio keeps running at jetsam priority band 'Audio and Accessory' (higher than ordinary background) under its normal per-process limit; suspended apps are evicted by memory pressure. Query headroom at runtime with os_proc_available_memory().
- ANDROID BASELINE PROFILES — fully applicable to RN apps via the standard androidx.baselineprofile Gradle plugin + Macrobenchmark module + baseline-prof.txt merged into the AAB (AGP 8+); Google cites ~30% cold-start improvement for native apps and Meta published production adoption (engineering.fb.com, 2025-10-01). For RN specifically, measured community gains are much smaller (~7% on RN 0.71) because startup is dominated by Hermes JS execution, which ART profiles cannot precompile. No first-class Expo/EAS integration exists as of 2026-07 — could not verify any claim that react-android ships its own baseline profile; adding one to an Expo app requires a config plugin because SDK 57's `expo prebuild` now clears and regenerates native directories by default.

### Recommendations for DeenDawn

- Enable Worklets Bundle Mode for production builds NOW (worklets 0.10 is already in the SDK 57 dependency tree via reanimated 4.5). This directly protects DeenDawn's background-audio memory footprint from the 25–30% Hermes V1 + reanimated regression. Verify before/after with Xcode Instruments (Allocations) and the DevTools Memory panel on a release-mode build, not dev (dev-mode Bundle Mode memory is misleadingly high — issue #9913).
- Standardize the profiling toolkit: (1) React Native DevTools (`j` in Metro) Profiler + Memory panels for dev; (2) Rozenite with the performance-marks and network plugins for flow-level timings (also useful to audit that the ONLY outbound calls are to the R2 bucket — supports the privacy invariant); (3) react-native-release-profiler for release-build startup traces opened in Perfetto/Speedscope. All of these are local dev tooling with no shipped telemetry, so they preserve 'Data Not Collected'. Do NOT adopt Sentry, Firebase Perf, or EAS Insights — all would violate rule 2.
- Add a bundle-size gate to the release checklist: `EXPO_ATLAS=true npx expo export` then `npx expo-atlas .expo/atlas.jsonl`; record JS bundle size next to the existing <100 MB binary / <25 MB quran.db budgets and investigate any release-over-release jump >10%.
- Trial React Compiler on a branch: set `experiments: { reactCompiler: true }` in app config, run the health check, and measure surah-list scroll and tasbih-tap re-render counts with the DevTools Profiler. Expect ~20–40% fewer re-renders where memoization is missing. Because it is still experimental on SDK 57, gate merging on the full Maestro E2E suite passing in all three locales; log the decision in docs/DECISIONS.md.
- Quran reader lists: adopt/keep FlashList v2 semantics — drop any estimatedItemSize remnants, keep maintainVisibleContentPosition default (it prevents jumps when translation toggling resizes ayah rows), hold per-ayah UI state (expanded translation, playing indicator) in useRecyclingState so recycled rows reset correctly, and set maxItemsInRecyclePool only if profiling shows memory pressure from many distinct item types.
- Set concrete budgets: cold start <2.0s TTI on iPhone 12 AND Pixel 6a-class (matches 2026 premium norms; measure TTID and TTFD separately with performance.mark + the W3C-aligned PerformanceObserver in RN 0.86); steady-state memory during background Quran audio playback <250 MB (comfortable margin under the ~900 MB limit of 3 GB iPhones, the realistic floor for DeenDawn's audience); assert headroom in a device-pass test via os_proc_available_memory(). Add both to docs/TESTPLAN.md 'Device pass (human)'.
- For the Android release phase (after iOS TestFlight): add Baseline Profiles via an Expo config plugin that wires the androidx.baselineprofile plugin and a Macrobenchmark module at prebuild time — never hand-edit android/ (SDK 57 prebuild wipes it). Size expectations honestly: ~5–10% cold-start gain for an RN app, not the 30% native-app headline, because Hermes bytecode already handles the JS side. Schedule it alongside the mandatory 14-day/12-tester closed test so benchmarking devices are available.

### Pitfalls

- react-native-startup-profiler does not exist — if any doc or plan references it, replace with react-native-release-profiler + Xcode Instruments/Macrobenchmark. Most 'Flipper profiling' tutorials still ranking in search are obsolete (Flipper deprecated RN 0.73, removed from templates 0.74).
- The reanimated memory regression hits even apps that never call reanimated APIs — importing it is enough. DeenDawn ships reanimated 4.5, so this applies by default until Bundle Mode (or the future Hermes fix) is enabled.
- Never benchmark memory or startup in dev builds: Bundle Mode dev memory is inflated (~4x bundle per worklet runtime), and Hermes debug builds skip bytecode precompilation. Release builds only.
- SDK 57 `expo prebuild` clears and regenerates native directories by default — any manual Gradle changes for baseline profiles/macrobenchmark (or anything else) will be silently destroyed; config plugins are the only durable path.
- React Compiler on Expo is experimental despite React Compiler v1.0 being 'stable' upstream — the two statuses are different things; don't treat react.dev's stability announcement as Expo sign-off.
- iOS memory limits are per-device, not per-app-category: the ~2098 MB iPhone 12 figure collapses to ~900 MB on iPhone SE-class hardware, and background-audio priority only delays eviction, it doesn't raise the limit. Budget for the worst supported device.
- FlashList v2 is New-Architecture-only (fine for this repo) and its maintainVisibleContentPosition default has known edge-case bugs when initial data doesn't fill the screen (Shopify/flash-list #2050) — test short surahs (al-Kawthar, 3 ayahs).
- Community '40% cold start' claims (New Architecture, Hermes V1, Baseline Profiles) come from marketing-adjacent posts; the only RN-specific baseline-profile measurement found was ~7%. Treat headline percentages as upper bounds, and verify the unconfirmed claim that RN ships its own baseline profile before relying on it (could not be verified this session).

## store-conversion: App Store + Google Play listing conversion best practice 2026 for DeenDawn: screenshots, preview video, Islamic-app ASO + Ramadan 2027 seasonality, custom product pages / custom store listings for ar/ur, and review-prompt timing

### Key findings

- SCREENSHOT SPECS (Apple, fetched 2026-07-31): 1-10 screenshots per locale, JPEG/PNG, no alpha. Only two sizes are mandatory: iPhone 6.9-inch (1320x2868 portrait; 6.5-inch 1284x2778 accepted as fallback) and iPad 13-inch (2064x2752) if the app runs on iPad; all other sizes auto-scale from these. (developer.apple.com screenshot-specifications)
- SCREENSHOT CONVERSION PATTERNS (AppFollow guide updated 2026-06-02 + 2026 industry guides): the first 2-3 frames carry ~60-70% of conversion weight; captions under 5 words / ~30 chars, top-stacked, rendered ~60pt+ so they survive thumbnail size; portrait orientation wins for utility apps; concrete benefit captions beat generic ones ('Everything in one app' underperforms). Device-framed screenshots tend to read as more credible for utility/prayer apps while full-bleed wins in social/entertainment — this is directional industry consensus, not Apple data, and is A/B-dependent.
- LOCALIZED CREATIVES: localized (market-specific imagery/tone) screenshots significantly outperform merely translated ones (AppFollow, 2026-06-02). Sensor Tower's Islamic-app creative analysis (Sep-Oct 2025 data) shows France-market winners use Arabic calligraphy verses + translation over nature backdrops, US winners lead with prayer times / qibla / Quran utility, Malaysia winners lead with qibla + Kaaba distance.
- PREVIEW VIDEO SPECS (Apple, fetched 2026-07-31): 15-30 seconds, max 500MB, H.264 (10-12 Mbps, max 30fps, .mov/.m4v/.mp4) or ProRes 422 HQ, stereo AAC 256kbps, up to 3 previews per locale, poster frame defaults to 5s in. iPhone portrait preview resolution is 886x1920.
- PREVIEW VIDEO VALUE FOR UTILITY APPS: 2026 guides converge on video being optional/low-ROI for utility and productivity apps (screenshots first); a weak video can reduce conversion ~10-15% vs no video, while a strong one lifts 10-25%. No category-specific data exists showing video helps prayer/worship apps specifically — this is a test-later item, not a launch requirement. (semnexus.com, screenfast.app, splitmetrics.com — secondary sources)
- ISLAMIC APP ASO LANDSCAPE (Sensor Tower, Sep-Oct 2025 data): on iOS US, ~90% of keyword-driven installs for leading Islamic apps come from BRANDED app-name variations; Google Play US is more diversified across functional terms (prayer times, athan, qibla, quran) plus competitor-brand terms. ## haptics-sound-design: Haptic + sonic design for DeenDawn (Expo SDK 57, 2026): expo-haptics vs CoreHaptics/VibrationEffect, custom-waveform libraries, haptic grammar, UI sound conventions, and worship-app patterns (tasbih, prayer-time, qibla)

### Key findings

- expo-haptics in SDK v57 (docs dated 2026) exposes ONLY presets: impactAsync (Light/Medium/Heavy/Rigid/Soft), notificationAsync (Success/Warning/Error), selectionAsync, plus Android-only performAndroidHapticsAsync with ~20 HapticFeedbackConstants values (Clock_Tick, Confirm, Reject, Segment_Tick, Segment_Frequent_Tick, Keyboard_Tap, Toggle_On/Off, Virtual_Key, Long_Press, Gesture_Start/End, Drag_Start, etc.). No custom waveforms, no AHAP, no CoreHaptics pattern API. VIBRATE permission is auto-added. iOS Taptic Engine is silently disabled in Low Power Mode, when the user disables system haptics, when the camera is active, and during dictation. (docs.expo.dev/versions/latest/sdk/haptics, verified as v57.0.0, fetched 2026-07-31)
- Custom waveforms ARE possible in an Expo project, but only via third-party native modules (dev build / prebuild required — fine for DeenDawn which already uses CNG). Best current option: react-native-haptic-feedback v3.0.0 (npm latest as of 2026-07-31, MIT, RN >=0.71 peer dep, ships codegenConfig for New Architecture). v3 goes far beyond its old preset-trigger API: iOS uses a 3-tier fallback (CHHapticEngine CoreHaptics -> UIFeedbackGenerators -> AudioServices), Android uses performHapticFeedback -> VibrationEffect composition primitives (API 31+) or waveforms (API 26+). It adds triggerPattern() with either a compact string notation ('o' medium, 'O' heavy, '.' light, ':' soft, '-' 0.1s pause, '=' 1s pause) or HapticEvent[] arrays with per-event millisecond timing, intensity, and sharpness, plus built-in Patterns (success, error, warning, heartbeat) and a cross-platform AHAP wrapper (plays .ahap on iOS, falls back to triggerPattern on Android). AHAP files require manual Xcode Build Phases setup (github.com/mkuczera/react-native-haptic-feedback, registry.npmjs.org)
- react-native-nitro-haptics 0.2.3 (oblador, MIT) is a Nitro-modules 'drop-in replacement for expo-haptics' built for New Architecture, whose differentiator is low latency and worklet support: NitroModules.box(Haptics) lets you fire haptics directly from Reanimated worklets on the UI thread even when the JS thread is busy. Presets only (impact/notification/selection + ~16 Android HapticFeedbackConstants) — no custom patterns. Requires react-native-nitro-modules peer. Pairs naturally with DeenDawn's reanimated 4.5. (github.com/oblador/react-native-nitro-haptics, registry.npmjs.org)
- Other custom-pattern libs are weaker fits: @candlefinance/haptics (MIT) plays CoreHaptics patterns + .ahap on iOS but merely 'vibrates' on Android, and the repo's last push was 2024-11-02 (~21 months stale, verified via GitHub API); react-native-hapticlabs (MIT) plays AHAP on iOS and HLA/OGG/HAC HD-haptic files on Android with device support-level detection 0-4, but patterns must be authored in the proprietary Hapticlabs Studio no-code tool and the repo is niche (9 stars); SimformSolutions/react-native-haptic-patterns is low-activity (22 commits, 6 stars) and its patterns are just timed vibrate/pause sequences — the 'buzzy' style Google explicitly warns against.
- Apple's haptic grammar (HIG 'Playing haptics' + UIFeedbackGenerator docs, corroborated via multiple sources): selection = the subtlest, for moving through discrete values (pickers, dials); impact light/soft = small UI collisions and taps, medium = elements snapping into place, heavy/rigid = large collisions; notification success/warning/error = task outcomes, used sparingly. System components (pickers, switches, sliders) already emit haptics automatically. Core Haptics (transient + continuous events with per-event intensity and sharpness, optional AudioCustom audio) is the escape hatch for choreographed experiences. Apple's WWDC21 'Practice audio haptic design' session gives three principles for combining sound + haptics: CAUSALITY (feedback source must be obvious), HARMONY (feel matches look and sound — small things feel/sound small; a continuous haptic should pair with continuous audio, not transient pulses), UTILITY (feedback only for significant moments, never novelty). (developer.apple.com/videos/play/wwdc2021/10278)
- Google's haptics design principles (developer.android.com/develop/ui/views/haptics/haptics-principles, fetched 2026-07-31): three classes — 'clear' (crisp, mechanical, use HapticFeedbackConstants / predefined VibrationEffects), 'rich' (sequenced composition primitives: CLICK, TICK, LOW_TICK short; SLOW_RISE, QUICK_RISE, QUICK_FALL, THUD, SPIN chirps), and 'buzzy' (avoid for touch feedback). Rules: frequent events get very subtle effects, important events get stronger ones; progressively increase amplitude as an interaction approaches its target (drag/snap — directly applicable to qibla alignment); be consistent per interaction type; co-design with visuals and audio (out-of-sync haptics feel like device malfunction); NEVER use legacy one-shot vibrations (Vibrator.vibrate, createOneShot) — good haptic feedback is 10-20 ms; 'less is more' — overuse numbs hands and drives users to disable haptics. Critical caveat: if a VibrationEffect.Composition contains ANY primitive the device doesn't support, the ENTIRE composition silently plays nothing — always check support and provide fallbacks.
- UI sound conventions in premium apps (Design+Code UI Sound Design handbook; 'Acoustic UX' 2025-2026 articles): silence is the premium default — restraint makes the few sounds meaningful; reserve sound for task outcomes and moments users may not be looking at the screen (Apple Pay's two-tone confirmation chime, Slack's low-intensity notification chimes cited as exemplars); lower/warmer tonalities read as stable and premium while bright synthetic tones read as cheap; frequent low-priority actions (scrolling, tapping) should stay silent; test on both phone speaker and earbuds (midrange survives, deep bass disappears on phone speakers).
- Verified worship-app patterns in shipping apps (App Store / Play listings, fetched 2026-07-31): tasbih — Sebha does haptic on every tap + a distinctly STRONGER vibration at every 33rd count; Tasbih Tally does per-click haptic + 'tactile cycle alert' at 33/99 completion; Tap Tasbih makes milestone vibration configurable (33rd/100th/200th/500th); Simple Tasbih Counter uses a subtle per-tap vibration with 33/99 targets. Qibla — Qibla Finder: Offline Compass gives 'a gentle vibration when you're perfectly aligned'; HalalLens Qibla Finder vibrates once when heading comes within 5 degrees of qibla. The established grammar: continuous subtle tick while counting, escalation at religiously meaningful milestones, and a single one-shot confirmation (not continuous buzzing) at qibla alignment.
- expo-audio in SDK 57 now supports genuine low-latency short sounds: the long-standing 'no real preloading' problem (expo/expo#42900, opened 2026-02-05 — buffering only began after play(), making expo-audio unusable for UI sound effects) was fixed by PR #43061 (merged 2026-02-19, iOS; companion PRs #43062 Android, #43063 web). SDK 57 docs now document Audio.preload(source, {preferredForwardBufferDuration}) for 'near-instant playback', player reuse via replace(), the seekTo(0)+play() replay pattern, and interruptionMode 'mixWithOthers' described as 'best suited for sound effects, UI feedback, or short audio clips'. No extra native dependency is needed for subtle UI sounds. (docs.expo.dev/versions/latest/sdk/audio, verified v57)

### Recommendations for DeenDawn

- Baseline: stay on expo-haptics for the whole v1 grammar — it covers everything DeenDawn strictly needs. Define a single semantic haptic module (e.g., src/lib/haptics.ts) mapping app events to one preset each, used everywhere for consistency: tap/toggle -> selectionAsync (iOS) / performAndroidHapticsAsync(Virtual_Key or Keyboard_Tap); snap-into-place (settings pickers, method/madhab) -> impactAsync(Light); task outcome -> notificationAsync(Success). On Android prefer performAndroidHapticsAsync over the iOS-style emulation — it uses HapticFeedbackConstants, respects system haptic settings, and matches Google's 'clear haptics' guidance.
- Tasbih bead feel (the one place worth going beyond presets): per-tap = iOS impactAsync(Soft) or selectionAsync, Android performAndroidHapticsAsync(Segment_Frequent_Tick) — Google's designated constant for exactly this rapid-repeat case; at 33/66 = impactAsync(Medium) or Android Segment_Tick/Confirm; at 99/target = notificationAsync(Success). This mirrors the verified market grammar (Sebha, Tasbih Tally, Tap Tasbih). If you want a genuinely premium 'bead slides then settles' feel, add react-native-haptic-feedback v3.0.0 (New-Arch codegen, RN>=0.71 — compatible with RN 0.86/SDK 57 prebuild) and author the milestone celebration as a HapticEvent[] pattern (e.g., three ascending soft transients ~80ms apart) — skip .ahap files (they need manual Xcode Build Phases, which fights CNG/prebuild; the HapticEvent[] API is equivalent and survives prebuild cleanly). Since tasbih taps are driven by fast repeated presses and DeenDawn runs reanimated 4.5, optionally use react-native-nitro-haptics boxed into a gesture worklet so the tick never lags behind the finger when the JS thread is busy — but treat it as a polish-phase addition (v0.2.3, young library), not a foundation.
- Qibla alignment: implement Google's 'progressive interaction' pattern with hysteresis. While rotating far from qibla: silence. Entering a coarse window (~15 degrees): sparse selectionAsync ticks throttled to heading changes (never per sensor frame). On entering the aligned window (±5 degrees, matching shipping qibla apps): ONE impactAsync(Medium) + visual state change; re-arm only after leaving a wider window (e.g., ±8 degrees) so micro-jitter never machine-guns the motor. Never run a continuous vibration while aligned — that is Google's 'buzzy' anti-pattern and drains battery. Since heading comes from expo-sensors on the JS thread, throttling in JS is fine; worklet-driven haptics is again optional polish.
- Prayer-time arrival: background arrival is a notification, so the entire experience is the sound file — iOS plays its default vibration alongside; per-notification custom haptic patterns are not possible for standard notifications, and the <30s caf adhan clips (already in the constitution) are the design surface. Choose clip onsets that are warm and low (matches brand + premium convention) rather than bright/synthetic. If the app is foregrounded at prayer time, play notificationAsync(Success)-class haptic + an optional soft chime through the in-app path instead of relying on the notification.
- Sound policy for a worship app: default to silence everywhere except adhan/prayer notifications. No per-tap tasbih sound by default (users make dhikr in mosques, at work, in bed) — offer an optional 'subtle click' toggle, OFF by default; if enabled, use SDK 57's Audio.preload() at module scope + a reused player with seekTo(0)+play(), audioMode interruptionMode 'mixWithOthers' + playsInSilentMode false so the iOS mute switch is respected for UI sounds (worship etiquette: the hardware silent switch must win). Qibla 'found' can be haptic-only — every shipping qibla app verified uses vibration, not sound. Do NOT add a third-party audio lib for UI sounds; the Feb 2026 preload fix makes expo-audio sufficient and keeps the dependency tree minimal (privacy posture).
- Respect user control and accessibility: one Settings toggle 'Haptic feedback' (and the optional sounds toggle) gating the semantic haptics module centrally; on Android, performAndroidHapticsAsync/HapticFeedbackConstants already respect the system 'touch feedback' setting — don't bypass it via the Vibrator path. Document in TESTPLAN.md 'Device pass (human)' that haptics cannot be validated in the iOS Simulator (no Taptic Engine) and that iOS suppresses haptics in Low Power Mode and while the camera is active — testers should not file those as bugs.
- Follow the WWDC21 causality/harmony/utility test for every proposed haptic: it must have an obvious visible cause (bead advances, needle locks, prayer badge appears), match the visual weight (a bead is small -> soft/selection, never heavy), and carry information (count progress, milestone, alignment) — cut anything decorative. This keeps the app dignified, which is itself the correct 'premium worship' register.

### Pitfalls

- expo-haptics cannot do custom waveforms, AHAP, intensity/sharpness control, or timed patterns — chaining impactAsync calls with setTimeout produces the 'buzzy' legacy feel Google explicitly warns against; if you need a real pattern, use react-native-haptic-feedback's HapticEvent[] API instead of JS-timed preset spam.
- Android VibrationEffect.Composition silently plays NOTHING if any primitive in the composition is unsupported on the device — many mid-range Androids lack primitives entirely. Any custom-pattern code path needs a capability check and a HapticFeedbackConstants fallback (react-native-haptic-feedback v3 handles the tiering, but verify on a low-end device; DeenDawn targets API 24+ where even VibrationEffect waveforms only exist from API 26).
- .ahap file playback in react-native-haptic-feedback requires manually adding the files to Xcode Build Phases — this does not survive `expo prebuild` without writing a custom config plugin; prefer the in-JS HapticEvent[] pattern API which needs no resource wiring.
- @candlefinance/haptics looks attractive (AHAP + patterns) but last repo push was Nov 2024 and Android support is plain vibration only — do not adopt for a New-Architecture RN 0.86 app without testing; SimformSolutions/react-native-haptic-patterns builds duration-based vibrations (the 'buzzy' anti-pattern) and shows minimal maintenance.
- iOS silently disables the Taptic Engine in Low Power Mode, when system haptics are off, while the camera is active, and during dictation — haptic-only feedback must never be the sole confirmation channel (pair with visual state, per HIG multi-modal feedback guidance). Also nothing haptic is testable in the iOS Simulator; add device-pass items.
- expo-audio's Audio.preload() is new (merged 2026-02-19, SDK 57 docs) — older tutorials and pre-SDK-57 patterns (create player on tap, downloadFirst) still exhibit 100ms+ first-play latency; ensure preload happens at module scope before render, and reuse one player per sound.
- Adding react-native-haptic-feedback or react-native-nitro-haptics means a native module change: rebuild the dev client and re-run the iOS build gates (per constitution: prebuild + xcodebuild green before push). Nitro haptics also pulls in react-native-nitro-modules as a peer — one more native dep to audit; both are MIT and make zero network calls, so the privacy posture is unaffected, but log the dependency decision in DECISIONS.md.
- Do not put haptic calls inside per-frame sensor callbacks (qibla heading updates arrive many times per second) — throttle by degree-change and use hysteresis, or the motor saturates and users disable haptics app-wide (Google: 'too much vibration numbs hands').
- Apple's HIG 'Playing haptics' page is JS-rendered and could not be fetched verbatim this session; its pattern taxonomy was cross-checked via the WWDC21 session, Expo/Android docs, and secondary sources rather than the page text itself.
